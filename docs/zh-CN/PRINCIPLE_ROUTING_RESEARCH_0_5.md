# Vertex Palace 0.5 原理级路由研究

## 目标

研发重点改为修复通用信息流，不允许加入仓库名、issue 编号、特定路径或一次性关键词规则。

## 四项不变量

1. **任务动作优先**：用户要求执行的工程动作，高于生命周期和风险背景。被描述为 release blocker 的 bug 仍是 bugfix；真正要求 publish、tag 或 version 的任务才是 release。
2. **精确身份守恒**：任务明确给出的仓库路径、类、方法、函数、端点或测试身份，必须穿过评分、表面平衡、扩张、剪枝与最终截断。存在歧义时必须报告，不能静默换成别的文件。
3. **长文本证据有上限**：issue 正文重复出现的宽泛词，不能靠数量压过精确身份与可执行子句。正文只能补充证据面，重复不等于无限加分。
4. **真值必须可观测**：静态路由召回率只对 base commit 中已经存在的文件计硬分。隐藏解法新建的文件属于结果真值，必须单独报告，不能要求路由器预知未来路径。

## 防止研发死循环

- 已揭盲目标永久关闭调参资格，只能保留为回归证据。
- 生产代码禁止出现目标仓库名、issue 编号、冻结路径或目标专用别名。
- 每类失败最多进行一次通用机制修复；若经过修复后又连续两轮新目标失败，就停止案例修补，转入架构复审。
- 分开评价解析器、分类器、路由器、Context 契约与真实 Agent 效率。
- 只有双方都成功产生结果时才能比较 Token 和速度；失败条件不能记成零。

## 当前假设

- `releaseIntent` 过于宽松，把没有发布动作的 release 风险描述也当成任务意图。
- 精确对象识别本身已经有效，但最终路线没有把符号身份当作强制契约。
- 当前隐藏 diff 真值混合了 base 可见文件与解法中新建的文件。

## 当前证据

- 不含真实仓库专用词的中性动作与身份 fixture 已通过。
- 产品完整测试通过：core 281 项、MCP 2 项、CLI 3 项、研究测试 274 项；另有 2 项按设计跳过。
- 在已揭盲的 V6 回归中，任务从 `release` 修正为 `bugfix`；因为 `RenderSlotTagHandler._render_value` 得到身份守恒，`python/djust/components/function_component.py` 成为第一 Primary 来源。
- `content`、`value`、`str` 等示例值不会再因为出现在代码格式中，或只是限定方法名的子串，就被升级成强制路线身份。
- 这次披露回归交付约 1,353 个估算 Context Token，但仍耗时约 96 秒，并保留一个有噪声的协调来源。它只能作为回归证据，不能当成新资格结果或速度声明。
- V6 聚焦测试文件是隐藏 diff 新建的。原结果仍为负面，因为候选版漏掉了 base 可观察实现；后续新建文件任务必须以预注册的可观察创建位置计分。

## 尚未解决

- 限制长文本宽泛证据面，避免精确实现已经锁定后仍不断加入低价值支持文件。
- 把 Context 延迟从索引与路由质量中拆开，独立分析。
- 冻结本轮机制后，才能选择新的资格仓库。

## 验收顺序

1. 先加入与真实目标无关、修改前会失败的中性 fixture。
2. 修复任务动作优先级和精确身份守恒，不加入目标词汇。
3. 运行聚焦测试、完整 workspace 测试、build、lint、MCP smoke 与 release-candidate 检查。
4. 已揭盲目标只作回归，失败记录保持原样公开。
5. 冻结候选后，再机械选择另一个全新仓库进行资格测试。

任何单一历史目标都不能证明 0.5 达标。
