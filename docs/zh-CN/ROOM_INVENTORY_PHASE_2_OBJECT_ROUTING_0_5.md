# Room Inventory 0.5：第二阶段对象关系与路由

状态：开发候选已验证；除非明确开启 Room Inventory 索引，否则仍使用默认 0.4 行为。

## 目的

第二阶段开始使用第一阶段写入的可选对象元数据，在既有 Palace 图谱上增加有界对象关系与精确对象身份评分。它不会建立第二套图，也不会因为对象精确命中就宣称任务证据已经完整。

这些是开发证据，不是 Round 26 资格结果，也不是 Agent 性能结论。

## 对象关系

只有索引节点含有 Room Inventory 元数据时才会建立对象关系：

- `contains`：Owner 类、类型、接口或对象拥有某个命名成员。
- `calls`：对象正文引用了一个全仓唯一声明。
- `tests` 与 `tested_by`：保守识别出的测试对象引用一个唯一实现对象。

关系构建使用倒排引用索引。局部声明名称必须在仓库中唯一，正文引用才能建立关系；存在同名声明时不会猜测调用目标。动态派发和无法解析的引用保持未连接状态。

每个来源对象最多保留 32 条新推断关系。应用上限前，会按测试证据、Owner 结构、调用证据、解析置信度与确定性目标身份排序。

## 对象优先评分

只有节点含有可选对象元数据时才会启用对象评分，顺序如下：

1. 完整身份，例如 `PaymentService.authorize`。
2. 分别明确出现的 Owner 与成员标识符。
3. 明确的局部代码标识符，例如反引号中的 `authorize`。

如果多个对象共享同一个局部名称，它们会获得相同增益，不会被工具强行消歧。解析置信度只缩放身份增益，不能替代路线置信度、证据闭合、测试或运行验证。

既有证据增益扩张器现在把 `calls` 视为因果关系；原有上下文上限、连接度惩罚、角色闭合和停止规则继续生效。

## 精确对象烟雾结果

对于明确命名 `attachObjectMetadata` 的任务，本地构建候选（`node dist/palace.cjs`）把以下对象放在第一顺位：

```text
packages/core/src/parser/attach-object-metadata.ts:13-22
```

加载等级为 `full_symbol`，理由为 `exact Room Inventory object match`，聚焦 Room Inventory 测试也进入同一条有界路线。由于证据闭合仍不足，整体路线置信度保持 `0.4`；这是预期的安全行为。

本次开发测试期间，全局安装的 `palace` 命令仍是稳定版 0.4，不把它当作 0.5 候选。烟雾测试完成后已恢复默认、不含对象记录的索引。

## 兼容与声明边界

- 默认索引不写入对象元数据或对象关系。
- 既有节点 ID、CLI/MCP schema、Palace 模式和上下文上限不变。
- 对象命中不能越过任务补全或拒答。
- 单独对象命中不能授权强制停止。
- 当前证据不能证明 Agent 更正确、节省 Token、减少工具调用或更快完成。
