## 实际变化

Httprouter 从 `tree.go, router_test.go` 改为完全符合 oracle 的 `tree.go, tree_test.go`。任务缩写 `TSR` 能展开到实现符号标题，且具有辨识度的根目录同模块结构可以补入正确测试；这条规则没有使用仓库名称或题目编号硬编码。

模块配对 v1 也把 Jinja 从 5 个路线文件扩张到 7 个，误带入 `src/jinja2/tests.py` 和 `tests/test_runtime.py`。原因是第一版允许任何较强结构证据在测试文字证据薄弱时绕过门槛。收紧版 v2 只允许“被任务锚定的同模块镜像”使用该通道。Jinja 恢复为原本 5 个文件，Httprouter 仍保持完全命中，其余 7 个 v1 路线没有变化。

## 解读

1. 当同模块实现与测试结构受到高辨识度任务证据锚定时，它可以找回真正遗漏的测试。
2. 只有结构相似并不能证明文件属于当前任务；让结构证据单独绕过语义门槛会造成路线膨胀。
3. 收紧规则相对原始 held-out 结果产生了可归因的小幅静态路由改善，但这组已披露样本仍未通过任何整体验收门槛。
4. Execa 与 Mio 仍然高置信度地选错文件，因此置信度校准是当前最高优先级的安全问题。
5. Thiserror 已找到聚焦测试，却漏掉宏实现；下一步应利用套件与符号因果关系补召回，而不是再增加全局文件名权重。
6. Jinja 与 Httpcore 的辅助 changelog/config 文件不应混入核心实现/测试规则，应使用独立且有上限的辅助文件策略。

## 后续方向

- 当实现文件缺乏独立任务证据时压低 confidence，即使路线看起来形成了完整配对也不能例外。
- 先匹配精确实体与操作，再匹配一般行为词，重点处理 `peek`、tagged template、macro attribute 等任务。
- 使用测试到套件、符号依赖等关系，补回宏或生成代码任务中的间接实现。
- 将文档与配置辅助文件的召回独立出来，并设置严格上限。
- 未来修改先跑中性产品夹具，再跑本次已披露回归，最后才使用新冻结的 held-out 仓库集验证泛化。
