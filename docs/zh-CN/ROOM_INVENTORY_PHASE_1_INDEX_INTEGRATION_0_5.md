# Room Inventory 0.5：第一阶段索引整合

状态：已通过冻结开发夹具验证；面向生产的对象优先路由仍未启用。

## 目的

第一阶段把已冻结的 Room Inventory 身份契约接入现有解析器与节点索引。它只回答一个工程问题：Vertex Palace 能否保存函数、方法、类、类型和常量级元数据，同时不改变 0.4 的路由表面。

本阶段不宣称路由更准、节省 Token、Agent 更快，也不构成 Round 26 的资格结果。

## 启用方式

这项整合默认关闭。开发索引可通过以下环境变量开启：

```text
VERTEX_PALACE_EXPERIMENTAL_ROOM_INVENTORY=1
```

内部 `indexPalace` 与 `parseFile` API 也接受显式 `roomInventory` 选项，方便确定性测试；显式选项优先于环境变量。第一阶段不修改 CLI 与 MCP schema。

## 数据路径

1. 现有解析器继续用原来的方式发现 Symbol。
2. 只有开关开启时，中央元数据适配器才为受支持 Symbol 增加对象身份。
3. `buildNodes` 把可选元数据复制到既有 Symbol 节点。
4. 既有节点 ID、宫殿地址、摘要、标签、Token 成本、边、房间和打包输入都不会根据新元数据重新计算。

本阶段不增加对象关系边、对象优先评分、强制停止，也不会为每个对象生成 Markdown 文件。

## 开发阶段支持语言

| 语言 | 解析来源 | 置信度 | 导出证据 |
| --- | --- | ---: | --- |
| TypeScript / JavaScript | `ts-morph` | 1.00 | 明确模块导出或已导出的 Owner |
| Python | `python-structural` | 0.75 | 第一阶段不声称存在明确导出 |
| Go | `fallback-structural` | 0.65 | 声明名称大小写规则 |
| Rust | `fallback-structural` | 0.65 | 明确的 `pub` 声明 |

不支持的语言仍保留原有 Parsed Symbol，但不会写入 Room Inventory 元数据。

## 开发夹具结果

冻结的五语言夹具产生以下确定性索引结果：

| 指标 | 默认状态 | 开启 Room Inventory |
| --- | ---: | ---: |
| 文件 | 6 | 6 |
| 节点 | 22 | 22 |
| 边 | 36 | 36 |
| Symbol 节点 | 11 | 11 |
| 对象元数据 | 0 | 8 |
| 索引字节 | 67,746 | 75,386 |

索引体积倍率为 `1.1128`。既有节点路由字段投影一致率为 `1.00`；五个冻结目标对象在前方插入无关行后，declaration key 与 semantic hash 的保持率都是 `1.00`。

这些只是开发夹具证据，不满足 Round 26 所要求的全新目标、平衡顺序和重复执行条件。

## 兼容边界

- 默认保持关闭。
- 既有四种 Palace 模式与持久化 schema 版本不变。
- `object` 为可选字段，旧索引继续可读。
- 既有节点 ID 与路由输入不变。
- CLI 与 MCP 输入 schema 不变。
- 生产路由目前不会读取对象元数据。

## 下一阶段

第二阶段可建立有界对象关系和实验性对象优先候选。它必须遵守冻结的每对象最多 32 条边限制，把解析置信度视为来源证据而非路由置信度，并在开始 Round 26 目标选择前通过回归验证。
