# 分层路由验证协议（0.4.0-alpha.2，Round 22）

## 冻结边界

Round 22 使用 `../research/evidence/layered-routing-targets-round-22.json` 中的 12 个目标。在任一产品接触目标前，任务、语言、层次、核心真值、明确附属真值、潜在附属真值、冻结 GitHub 元数据、执行器、候选 tarball、baseline 包与门槛都会被哈希冻结。观察结果之后不得修改这些输入。

候选是 `vertex-palace@0.4.0-alpha.2`，baseline 是公开的 `vertex-palace@0.3.0`。每个目标的每个条件重复两次，条件顺序会按目标与重复次数反转，并且依序执行，不并行。

## 目标平衡

四种任务层次各 3 个：本地可识别、GitHub 元数据补全、高连接度跨文件、无法解析的控制任务。四个语言家族也各 3 个：TypeScript、Python、Go、Rust。

GitHub 元数据会在路由前冻结并哈希；正式试验读取冻结的一小时缓存。真实 GitHub 联网只作为独立 smoke test，不能改变静态路由结果。

## 真值分层

- 核心：实现文件与聚焦测试。
- 明确附属：任务或元数据明确要求的契约、配置、文档或 changelog。
- 潜在附属：只从隐藏 diff 或项目惯例得知，只作说明。

## 门槛

所有门槛必须同时通过：可访问引用补全 100%；控制任务拒答 100% 且零路线文件；可路由任务核心闭合 100%；宏观核心覆盖率至少 0.90；宏观 route focus 至少 0.70；每个可路由目标覆盖率至少 0.50、focus 至少 0.40；明确附属覆盖率 100%；双方共同完成目标的覆盖与 focus 非劣至少 -0.05；零过度自信、零错误强制停止、零 tracked-file 污染、零 payload 指标分歧；重复路线确定一致；候选 context 不超过 6000 估算 Token。

## 失败规则

第一次结果原样保存。失败会让稳定资格归零；最多进行一次通用机制修复，旧目标随后只作回归。同一失败类型经过一次通用修复后又在两轮全新研究连续失败，就暂停 0.4 stable 并进行架构复审。

Round 22 只提供静态路由证据，不能证明 Agent 正确率、Token、工具调用或时间改善。
