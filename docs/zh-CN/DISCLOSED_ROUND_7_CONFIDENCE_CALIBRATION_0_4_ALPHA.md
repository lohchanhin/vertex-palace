## 运作原理

当路线含有强关系或强结构的实现/测试配对时，原本的 evidence-sufficient core selection 可以把 confidence 上限放宽到 0.90。新规则只处理原本会得到该高上限的 bugfix 路线：从任务开头提取前两个有辨识度的锚点，并检查是否至少有一个所选实现符号能独立覆盖两者；如果没有，confidence 上限降为 0.15。

这不是仓库硬编码。产品测试使用中性的 `payload/escape` 结构与 `Fixes payload parsing for escaped newlines` 任务：路线保持不变，但因为没有任何实现符号同时独立覆盖 `payload` 与 `parsing`，所以 confidence 会被压低。

## 运行策略影响

- Execa 原本已经使用 `full-palace`，修改后维持不变，只是降低 confidence。
- Mio 因 confidence 低于窄上下文门槛，从 `route-lite` 改为 `full-palace`。
- Mio 的 context 估算从 1,804 增加到 2,440 Token。

这是刻意付出的安全成本。这项修复不会节省 context，而是防止证据不足的窄路线授权 Agent 过早聚焦。

## 解读

1. 先前的高分来自真实的 confidence cap 缺陷，不是环境噪声。
2. 如果实现本身没有独立命中任务开头的身份锚点，即使实现/测试配对看起来很完整，也不足以支持高 confidence。
3. 这项修复消除了已观察到的过度自信，但没有改变静态路线质量。
4. Execa 与 Mio 的路线仍然错误或不完整，召回问题必须由另一组证据选择修复处理。
5. Mio 目前刻意偏保守；必须使用新的 held-out 样本，才能判断这条上限在未知任务上是否过严。

## 后续方向

- 在再次调整上限前，先冻结一组新的 held-out 置信度校准样本。
- 分开衡量错误高 confidence 与错误低 confidence，并记录模式选择变化和实际交付 context 大小。
- 之后再用精确操作/实体锚点及因果符号关系修复召回，不能把校准改善与召回改善混为一谈。
- 除非未来端到端 Agent 实验支持，否则不得声称节省 Token 或时间。

## 声明边界

Vertex Palace 在这组已披露失败上变得更安全：Execa 与 Mio 不再获得高 confidence，Mio 也不再停留在狭窄的 `route-lite` 模式。但它仍未找到缺少的文件、仍未通过 Round 7 路由门槛，也没有证明效率提升。
