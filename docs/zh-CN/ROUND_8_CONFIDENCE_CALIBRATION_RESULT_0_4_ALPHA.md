# Round 8 置信度校准结果（0.4 Alpha）

## 结论

**独立实现锚点的置信度硬上限在未见目标上造成校准回归，不能继续作为分数规则；但它的
窄上下文安全意图应以独立的证据与授权机制保留。**

八个冻结目标中，基线与候选产生完全相同的有序路线。候选没有减少任何未见样本的过度
自信，却把低估目标从 4 个增加到 5 个，并把目标级校准平均绝对误差从 0.284 提高到
0.465。它让两个目标从 `route-lite` 转为 `full-palace`，消除了一个不安全窄模式目标，
同时在 16 条成对试验观察中多交付 792 estimated tokens。

这是静态路线证据，不是 Agent 效率结果。

## 环境补测

SQLAlchemy 没有被静默剔除。按预注册规则把每个条件的索引上限从两次 300 秒改为一次
900 秒后，候选索引用时 741,906 ms，基线索引用时 701,166 ms；两边随后都完成两次
确定性观察。

SQLAlchemy 在两个条件中的结果完全相同：

- 路线：`lib/sqlalchemy/orm/session.py` 与 `test/orm/test_session.py`
- 修改文件 coverage：0.33
- 路线 focus 与 precision：0.50
- 置信度：0.40
- 校准误差：0.07，属于 well-calibrated
- 模式：`full-palace`

它漏掉 `lib/sqlalchemy/orm/scoping.py` 与真正的 typing 测试
`test/typing/plain_files/orm/session.py`，同时加入无关的 session 测试。这是产品路线失败，
不是环境失败。

## 产品决定

1. 撤回二元 `0.15` 硬上限作为路线置信度评分规则。
2. 把独立锚点结果保留为明确的路线证据。
3. 自动 `bypass` 与 `route-lite` 必须独立满足窄化证据，不再只看显示的置信度分数。
4. 证据不足时保持 advisory，并让自动选择进入 `full-palace`；用户明确 override 仍是 override。
5. 先用中性夹具与已公开回归验证分离机制，再用新的未见集合判断能否泛化。

这不代表旧基线置信度已经校准。Round 7 已经发现已知的错误高分。下一版校准模型必须是
经验驱动、渐进式的，而不是二元压低分数；安全授权仍应保持保守。

## 下一步路线方向

更大的产品问题仍是路线质量。下一轮修复应针对已观察遗漏，同时不改写本轮证据：

- 区分 Sinon 文档示例与真正的实现/测试修改表面；
- 把 SQLAlchemy 的 `Session` typing 任务连接到 scoped-session 转发与 typing 测试；
- 找回 Viper 的第三个修改实现/测试表面；
- 在保留 Crossbeam 有界四文件路线的同时找回缺失文件；
- 在不丢失两个 oracle 文件的前提下减少 Rich 的六个额外文件。

下一轮未见目标仍是 `coverage >= 0.90`、`focus >= 0.75`，路线文件不超过 9 个。

## 声明边界

Round 8 支持一个安全架构决定：置信度校准与窄上下文授权应该分开。它不能证明 Agent
正确率、Token 节省、工具调用减少、总耗时缩短，或相对纯 Codex 的效率优势。
